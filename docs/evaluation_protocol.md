# Протокол evaluation pipeline и наивного прогноза

## Назначение этапа

Этап создаёт единый контракт прогнозов и расчёта метрик, который далее будут
использовать ARIMA, LSTM и ARIMA-LSTM. В рамках этапа реализуется только
наивная модель дневной логарифмической доходности:

```text
r_hat[t+1] = 0
```

Результаты рассчитываются раздельно для train и validation. Train используется
для описательной диагностики, а validation — для сравнения моделей и принятия
решений. Final test на этом этапе не оценивается.

## Границы этапа

В этап входят:

- проверяемая загрузка обработанного модельного набора;
- общий структурный интерфейс прогнозирующих моделей;
- наивная модель с нулевым прогнозом доходности;
- формирование стандартной таблицы прогнозов;
- расчёт абсолютных и относительных метрик;
- выполненный notebook с отдельными результатами train и validation.

В этап не входят обучение ARIMA, LSTM и ARIMA-LSTM, общий интерфейс `fit`,
expanding-window backtest, оценка final test и сохранение прогнозов в CSV.

## Входные данные

Evaluation pipeline использует обработанный снимок:

```text
data/processed/next_trading_day_returns.csv
data/processed/next_trading_day_returns.manifest.json
```

До использования данных загрузчик сверяет SHA-256, размер файла, число строк и
обязательные столбцы с манифестом. Каждая строка описывает доступную дату
`date`, прогнозируемую дату `target_date`, тикер, текущие рыночные значения,
целевую доходность следующего торгового дня и временную выборку.

Pipeline принимает модельный набор со всеми тремя временными выборками, но до
вызова модели оставляет только `train` и `validation`. Поэтому final test не
передаётся в `predict` и не может повлиять на прогнозы или метрики текущего
этапа.

## Интерфейс прогнозирующей модели

Модели передаются в pipeline через структурный интерфейс `ForecastModel`:

```python
class ForecastModel(Protocol):
    @property
    def name(self) -> str: ...

    def predict(self, observations: pd.DataFrame) -> pd.Series: ...
```

Модель не обязана явно наследоваться от `ForecastModel`, но должна соблюдать
его контракт:

- `name` — непустой строковый идентификатор;
- `predict` возвращает `pd.Series` с именем `predicted_return`;
- длина и индекс результата совпадают с переданными наблюдениями;
- прогнозы являются конечными числовыми значениями;
- входной `DataFrame` не изменяется.

Наивная модель имеет идентификатор `naive_zero` и возвращает `0.0` для каждого
наблюдения.

## Контракт таблицы прогнозов

Результат каждой модели содержит ровно следующие столбцы:

```text
date, target_date, ticker, split, model, actual_return, predicted_return
```

Одна строка соответствует одному прогнозу доходности следующего торгового дня.
Ключ `ticker, target_date, split, model` должен быть уникальным. Результат
сортируется по `split, ticker, target_date, model`. Строки final test в таблице
прогнозов запрещены.

## Метрики

Пусть `y[i]` — фактическая доходность, `y_hat[i]` — прогноз модели, а
`e[i] = y[i] - y_hat[i]` — ошибка. Доходность переводится в базисные пункты с
коэффициентом `BPS_FACTOR = 10 000`.

Для каждой группы рассчитываются:

```text
MAE_bps = BPS_FACTOR * mean(abs(e))
RMSE_bps = BPS_FACTOR * sqrt(mean(e^2))
RelMAE = MAE_model / MAE_naive_zero
OOS_R2 = 1 - MSE_model / MSE_naive_zero
DirectionalAccuracy = mean(sign(y_hat) == sign(y))
```

Метрики рассчитываются раздельно для каждой комбинации `split, ticker, model`.
Дополнительно создаётся строка `ticker = "ALL"`, рассчитанная непосредственно
по всем наблюдениям соответствующих `split` и `model`. Усреднение готовых
метрик отдельных тикеров для строки `ALL` не применяется. Train и validation
никогда не объединяются в одну метрику.

Каждая кандидатная модель должна иметь точно те же ключи
`split, ticker, target_date`, что и `naive_zero`, и одинаковые фактические
доходности для совпадающих ключей. Если ошибка baseline равна нулю, RelMAE и
OOS R² математически не определены, поэтому расчёт завершается `ValueError`.

Directional accuracy наивной модели не имеет содержательной интерпретации:
нулевой прогноз имеет знак `0` и совпадает с фактическим направлением только
при точной нулевой доходности.

## Проверки корректности

Компоненты этапа отклоняют данные до расчёта результатов, если обнаружены:

- пустая таблица или отсутствие обязательных столбцов;
- неизвестная временная выборка;
- дублирующиеся ключи наблюдений;
- нечисловые, пропущенные или бесконечные доходности и прогнозы;
- отсутствующий baseline;
- несовпадение ключей или фактических доходностей между моделями;
- некорректное имя модели или нарушение контракта `predict`;
- несоответствие обработанного снимка его манифесту.

Входные таблицы не мутируются. Нарушения контракта завершаются `ValueError`, а не созданием частичного результата.

## Воспроизводимость

Выполненный notebook
[`04_evaluation_baseline.ipynb`](../notebooks/04_evaluation_baseline.ipynb)
загружает проверенный снимок, запускает `NaiveModel`, рассчитывает метрики,
выводит train и validation отдельно и визуализирует распределения ошибок по
тикерам. Notebook содержит assertions, подтверждающие отсутствие final test,
`RelMAE = 1` и `OOS R² = 0` для baseline.

Повторное выполнение из корня проекта:

```bash
poetry run jupyter execute notebooks/04_evaluation_baseline.ipynb --inplace
```

Численные результаты хранятся в outputs notebook и не дублируются в протоколе.
Отдельный CSV с прогнозами на этом этапе не создаётся.

## Критерии завершения

- processed snapshot проверяется до использования;
- прогнозы train и validation соответствуют единому контракту;
- final test не читается моделью и не оценивается;
- метрики воспроизводимы и рассчитаны отдельно по выборкам;
- ноутбук выполнен без ошибок и содержит интерпретацию baseline;
- полный набор автоматических проверок проходит;
- в ветке отсутствует код обучаемых моделей.
